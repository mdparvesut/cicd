## 1. Understanding CI/CD Concepts

### 1.1 What is CI/CD?

**CI (Continuous Integration):**
- Automatically build and test code when changes are pushed
- Catch bugs early
- Ensure code quality before merging

**CD (Continuous Delivery/Deployment):**
- Automatically deploy tested code to servers
- Reduce manual deployment errors
- Fast, reliable releases

### 1.2 GitLab CI/CD Pipeline Flow

```
Developer pushes code
         ↓
GitLab detects .gitlab-ci.yml
         ↓
GitLab Runner executes pipeline
         ↓
    [Build Stage]
    - Compile code
    - Install dependencies
         ↓
    [Test Stage]
    - Run unit tests
    - Check coverage
    - Generate reports
         ↓
    [Deploy Stage] (we'll add in Step 4)
    - Deploy to VM
         ↓
    Success or Failure notification
```

### 1.3 Key CI/CD Terms

| Term | Definition | Example |
|------|------------|---------|
| **Pipeline** | Complete workflow from code to deployment | build → test → deploy |
| **Stage** | Group of jobs that run in sequence | `build`, `test`, `deploy` |
| **Job** | Individual task within a stage | `compile-backend`, `run-tests` |
| **Runner** | Server that executes pipeline jobs | GitLab's shared runners |
| **Artifact** | Files generated by jobs (saved for later stages) | Compiled binary, test reports |
| **Cache** | Speed up builds by saving dependencies | `node_modules/`, `go.mod cache` |

## 2. GitLab CI/CD Architecture

### 2.1 How GitLab CI/CD Works

```
┌─────────────────┐
│  Your Code Repo │
│  .gitlab-ci.yml │
└────────┬────────┘
         │
         │ (1) Push triggers pipeline
         ↓
┌─────────────────┐
│  GitLab Server  │
│  Reads pipeline │
│  configuration  │
└────────┬────────┘
         │
         │ (2) Assigns jobs to runners
         ↓
┌─────────────────┐
│  GitLab Runner  │
│  (Docker based) │
│  Executes jobs  │
└────────┬────────┘
         │
         │ (3) Reports results
         ↓
┌─────────────────┐
│  Pipeline UI    │
│  Shows success  │
│  or failure     │
└─────────────────┘
```

### 2.2 `.gitlab-ci.yml` Structure

```yaml
# Define stages (executed in order)
stages:
  - build
  - test
  - deploy

# Global settings
variables:
  VAR_NAME: "value"

# Job definition
job_name:
  stage: build           # Which stage
  image: golang:1.21     # Docker image to use
  script:                # Commands to run
    - go build
  artifacts:             # Files to save
    paths:
      - binary
```

## 3. Backend Pipeline - Build & Test

### 3.1 Complete Backend Pipeline

Create `reddit-clone-backend/.gitlab-ci.yml`:

```yaml
# ========================================
# GitLab CI/CD Pipeline for Backend
# ========================================

# Define pipeline stages (executed in order)
stages:
  - build
  - test

# ========================================
# Global Variables
# ========================================
variables:
  # Go configuration
  GO_VERSION: "1.21"
  CGO_ENABLED: "0"
  GOOS: "linux"
  GOARCH: "amd64"
  
  # Module cache (speeds up builds)
  GOPATH: $CI_PROJECT_DIR/.go

# ========================================
# Cache Configuration
# Speeds up pipeline by caching dependencies
# ========================================
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - .go/pkg/mod/

# ========================================
# STAGE 1: BUILD
# Compile the Go application
# ========================================
build:
  stage: build
  image: golang:${GO_VERSION}-alpine
  
  before_script:
    # Install build dependencies
    - apk add --no-cache git make
    
  script:
    - echo "Building backend application..."
    
    # Download dependencies
    - go mod download
    - go mod verify
    
    # Build the application
    - go build -o reddit-clone-backend -v .
    
    # Verify binary was created
    - ls -lh reddit-clone-backend
    - echo "Build completed successfully!"
  
  artifacts:
    # Save compiled binary for later stages
    paths:
      - reddit-clone-backend
    expire_in: 1 hour
  
  only:
    - branches
    - merge_requests

# ========================================
# STAGE 2: TEST
# Run unit tests and generate coverage report
# ========================================
test:
  stage: test
  image: golang:${GO_VERSION}-alpine
  
  before_script:
    # Install testing dependencies
    - apk add --no-cache git make
  
  script:
    - echo "Running unit tests..."
    
    # Download dependencies
    - go mod download
    
    # Run tests with coverage
    - go test -v -race -coverprofile=coverage.out -covermode=atomic ./...
    
    # Generate coverage report
    - go tool cover -func=coverage.out
    
    # Calculate total coverage percentage
    - |
      COVERAGE=$(go tool cover -func=coverage.out | grep total | awk '{print $3}' | sed 's/%//')
      echo "Total test coverage: ${COVERAGE}%"
      
      # Check if coverage meets minimum requirement (50%)
      if (( $(echo "$COVERAGE < 50" | bc -l) )); then
        echo "ERROR: Test coverage is below 50% (current: ${COVERAGE}%)"
        exit 1
      fi
      echo "Test coverage requirement met!"
  
  coverage: '/total:\s+\(statements\)\s+(\d+\.\d+)%/'
  
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage.out
    paths:
      - coverage.out
    expire_in: 1 week
  
  only:
    - branches
    - merge_requests

# ========================================
# OPTIONAL: Linting Job
# Check code quality and style
# ========================================
lint:
  stage: test
  image: golangci/golangci-lint:latest
  
  script:
    - echo "Running linter..."
    - golangci-lint run -v
  
  allow_failure: true  # Don't fail pipeline if linting fails
  
  only:
    - branches
    - merge_requests
```

### 3.2 Understanding the Backend Pipeline

#### **Build Stage Explained**

```yaml
build:
  stage: build
  image: golang:1.21-alpine      # Use official Go Docker image
```
- Uses Alpine Linux (lightweight, fast)
- Contains Go compiler and tools

```yaml
  before_script:
    - apk add --no-cache git make
```
- Installs additional tools needed for build
- `git` - for downloading Go modules
- `make` - for Makefile commands (optional)

```yaml
  script:
    - go mod download           # Download dependencies
    - go mod verify             # Verify checksums
    - go build -o reddit-clone-backend -v .
```
- `go mod download` - fetches all dependencies
- `go mod verify` - ensures dependencies haven't been tampered with
- `go build` - compiles the application

```yaml
  artifacts:
    paths:
      - reddit-clone-backend    # Save compiled binary
    expire_in: 1 hour           # Delete after 1 hour to save space
```
- Saves the compiled binary
- Can be downloaded from GitLab UI
- Used by later stages (like deploy)

```yaml
  only:
    - branches
    - merge_requests
```
- Only run on branch pushes and merge requests
- Saves pipeline minutes

#### **Test Stage Explained**

```yaml
test:
  stage: test
  script:
    - go test -v -race -coverprofile=coverage.out -covermode=atomic ./...
```
- `-v` - verbose output
- `-race` - detect race conditions
- `-coverprofile=coverage.out` - save coverage data
- `-covermode=atomic` - accurate coverage for concurrent code
- `./...` - test all packages

```yaml
    - go tool cover -func=coverage.out
```
- Shows coverage per function

```yaml
    - COVERAGE=$(go tool cover -func=coverage.out | grep total | awk '{print $3}' | sed 's/%//')
    - if (( $(echo "$COVERAGE < 50" | bc -l) )); then
        exit 1
      fi
```
- Extracts total coverage percentage
- Fails pipeline if below 50%
- Enforces minimum test coverage requirement

```yaml
  coverage: '/total:\s+\(statements\)\s+(\d+\.\d+)%/'
```
- Regular expression to extract coverage for GitLab's coverage badge
- GitLab displays this on the project overview

## 5. Unit Testing and Coverage

### 5.1 Why Unit Tests Matter

**Benefits:**
- ✅ Catch bugs before production
- ✅ Document how code should work
- ✅ Enable safe refactoring
- ✅ Required for course (50% coverage)

### 5.2 Backend Testing Strategy

According to course requirements, you must test:
1. **Password hashing/verification functions**
2. **Password change functionality**
3. **General business logic**

#### **Example Test Structure**

```
backend/tests/
├── auth_test.go           # Authentication tests
├── hash_test.go           # Password hashing tests
├── validation_test.go     # Input validation tests
└── post_test.go           # Post-related tests
```

#### **Example: Testing Password Hashing**

```go
// tests/hash_test.go
package tests

import (
    "testing"
    "your-module/internal/utils"
)

func TestHashPassword(t *testing.T) {
    password := "SecurePassword123!"
    
    // Hash the password
    hashed, err := utils.HashPassword(password)
    
    // Should not return error
    if err != nil {
        t.Errorf("HashPassword() error = %v", err)
    }
    
    // Hashed password should not equal original
    if hashed == password {
        t.Error("Hashed password should not equal original password")
    }
    
    // Hashed password should not be empty
    if len(hashed) == 0 {
        t.Error("Hashed password should not be empty")
    }
}

func TestVerifyPassword(t *testing.T) {
    password := "SecurePassword123!"
    hashed, _ := utils.HashPassword(password)
    
    // Test with correct password
    if !utils.VerifyPassword(hashed, password) {
        t.Error("VerifyPassword() should return true for correct password")
    }
    
    // Test with wrong password
    if utils.VerifyPassword(hashed, "WrongPassword") {
        t.Error("VerifyPassword() should return false for incorrect password")
    }
}

func TestHashPasswordDifferentResults(t *testing.T) {
    password := "SecurePassword123!"
    
    // Hash same password twice
    hash1, _ := utils.HashPassword(password)
    hash2, _ := utils.HashPassword(password)
    
    // Two hashes should be different (due to salt)
    if hash1 == hash2 {
        t.Error("Two hashes of same password should be different")
    }
}

func TestHashPasswordEmptyString(t *testing.T) {
    // Should handle empty password
    _, err := utils.HashPassword("")
    
    if err == nil {
        t.Error("HashPassword() should return error for empty password")
    }
}
```

## 6. Pipeline Artifacts

### 6.1 What Are Artifacts?

**Artifacts** = Files generated by pipeline jobs that you want to keep or use later.

**Examples:**
- Compiled binaries
- Build outputs (`dist/` folder)
- Test reports
- Coverage reports
- Logs

### 6.2 Configuring Artifacts

```yaml
job_name:
  artifacts:
    paths:
      - path/to/file
      - path/to/directory/
    expire_in: 1 week       # Auto-delete after 1 week
    when: always            # Save even if job fails
```

**Artifact expiration:**
- `1 hour` - For build artifacts (saves space)
- `1 week` - For test reports
- `1 month` - For important documentation
- `never` - Keep forever (not recommended)

### 6.3 Downloading Artifacts

**From GitLab UI:**
1. Go to **CI/CD → Pipelines**
2. Click on a pipeline
3. Click on a job (e.g., `build`)
4. Click **"Browse"** or **"Download"** button on the right

**Using GitLab API:**
```bash
# Download artifacts from latest successful pipeline
curl --header "PRIVATE-TOKEN: <your_token>" \
  "https://gitlab.com/api/v4/projects/<project_id>/jobs/artifacts/develop/download?job=build" \
  -o artifacts.zip
```

### 6.4 Using Artifacts Between Stages

Artifacts are automatically passed to later stages:

```yaml
build:
  stage: build
  script:
    - go build -o app
  artifacts:
    paths:
      - app

deploy:
  stage: deploy
  script:
    # The 'app' binary is available here
    - scp app user@server:/path/
  dependencies:
    - build  # Explicitly say we need build artifacts
```

## 7. Troubleshooting Pipelines

### 7.1 Common Pipeline Errors

#### **Error: "go: cannot find main module"**

```
error: go.mod file not found in current directory
```

**Solution:**
```yaml
# Make sure you're in the right directory
script:
  - cd backend  # If your code is in a subdirectory
  - go build
```

#### **Error: "npm ERR! missing script: build"**

```
npm ERR! missing script: build
```

**Solution:**
Check `package.json` has a build script:
```json
{
  "scripts": {
    "build": "vite build"
  }
}
```

#### **Error: "permission denied"**

```
/bin/sh: ./script.sh: Permission denied
```

**Solution:**
```yaml
script:
  - chmod +x script.sh
  - ./script.sh
```

#### **Error: "coverage below 50%"**

```
ERROR: Test coverage is below 50% (current: 35%)
```

**Solution:**
Write more tests! Focus on:
- Password hashing functions
- Authentication logic
- Validation functions

#### **View Job Logs:**
