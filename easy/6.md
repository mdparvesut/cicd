func HashPassword(password string) (string, error) {
    hashedBytes, err := bcrypt.GenerateFromPassword(

    err := bcrypt.CompareHashAndPassword(

## 🗣️ Part 9: Answering Individual Questions

### Common Questions & How to Answer

**Q: "How does your authentication work?"**
```
A: "We use JWT-based authentication. When a user logs in:
   1. We verify their password using bcrypt
   2. Generate a JWT token with their user ID
   3. Return the token to the client
   4. Client includes token in Authorization header
   5. Our middleware validates the token on each request
   
   Passwords are hashed with bcrypt cost factor 10, and we store
   only the hash in the database, never plain text."
```

**Q: "Show me the XSS protection implementation."**
```
A: "We use input sanitization. Let me show you...
   [Open utils/sanitizer.go]
   
   We use the bluemonday library to:
   1. Strip all HTML tags from user input
   2. Escape special characters like <, >, &
   3. Remove event handlers like onerror, onclick
   
   [Open post_handler.go]
   Every user input is sanitized before saving to database.
   
   [Demo in browser]
   If I try to create a post with <script>alert('XSS')</script>,
   it gets escaped and rendered as plain text."
```

**Q: "How do you handle secrets in your pipeline?"**
```
A: "We use GitLab CI/CD Variables for all secrets:
   [Open GitLab Settings → CI/CD → Variables]
   
   1. Secrets are stored as masked variables
   2. They're never committed to git
   3. We use Gitleaks to scan for accidental exposure
   
   [Open .gitlab-ci.yml]
   In the secrets-detection stage, if any secrets are found,
   the pipeline fails immediately before deploying.
   
   [Show deployment script]
   Secrets are injected as environment variables at runtime,
   never hardcoded in the application."
```

**Q: "What happens when you push code to main?"**
```
A: "The CI/CD pipeline automatically triggers:
   [Open GitLab Pipelines]
   
   1. Secrets Check - scans for exposed credentials
   2. Build - compiles frontend and backend
   3. Test - runs unit tests, checks coverage ≥50%
   4. Deploy - if everything passes:
      - SSH to VM
      - Copies new files
      - Runs database migrations
      - Restarts backend service
      - Application is live with new version
   
   The whole process takes about 3-5 minutes."
```

**Q: "How do you ensure database security?"**
```
A: "Multiple layers:
   1. Passwords are hashed with bcrypt before storage
   2. We use GORM ORM which prevents SQL injection
   3. Database only accepts local connections (not internet-facing)
   4. Credentials stored in environment variables, not code
   5. We use parameterized queries through GORM
   
   [SSH to VM, show]
   The database password is only in the systemd service file
   and is never visible in logs or code."
```

**Q: "Explain your real-time updates implementation."**
```
A: "We use WebSockets for bidirectional communication:
   [Show code]
   
   1. When frontend loads, it establishes WebSocket connection
   2. Backend maintains list of connected clients
   3. When any user creates/votes on a post:
      - Backend updates database
      - Broadcasts update to all connected WebSocket clients
      - Each client updates their UI in real-time
   
   [Demo with 2 browsers]
   Watch - I vote here [browser 1], and the count updates
   immediately here [browser 2] without refresh."
```

**Q: "How do you handle deployment failures?"**
```
A: "We have several safeguards:
   1. Pipeline runs tests before deploy - catches bugs early
   2. Deploy script backs up old binary
   3. Health check after deployment verifies it worked
   
   If deployment fails:
   [SSH to VM]
   We can rollback by:
   mv reddit-clone-api.backup reddit-clone-api
   systemctl restart reddit-clone-backend.service
   
   Logs help us diagnose:
   journalctl -u reddit-clone-backend.service
   tail -f /opt/reddit-clone/logs/backend.log"
```
